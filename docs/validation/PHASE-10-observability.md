# Phase 10 - Observability

**What this phase built:** kube-prometheus-stack from images mirrored into
ECR, the application's own ServiceMonitor, alerts and dashboard, the CloudWatch
observability add-on for Container Insights, a Grafana CloudWatch data source
with an IAM role of its own, and a dashboard for DocumentDB, RDS and the
cluster.

**Cost:** qa with its cluster, monitoring and the data tier is **$0.316/hr** by
`status.sh` - Phase 9's qa plus the `monitoring` endpoint - plus a few cents an
hour of Container Insights observations. The mirror is about 700 MB of
permanent ECR storage. Tear down at the end.

## 1. Mirror the images

Once per chart version. Applies the eight mirror repositories in the shared
stack, then copies into them.

```bash
# variable form
terraform -chdir=$PROJECT_ROOT/terraform/environments/shared plan -out=/tmp/shared.tfplan
terraform -chdir=$PROJECT_ROOT/terraform/environments/shared apply /tmp/shared.tfplan
$PROJECT_ROOT/scripts/mirror-images.sh --dry-run
$PROJECT_ROOT/scripts/mirror-images.sh
$PROJECT_ROOT/scripts/mirror-images.sh --check

# expanded
~/Documents/PROJECTS/mongo-dcu-pipeline/scripts/mirror-images.sh --check
```

The plan adds 16 resources: eight repositories and their lifecycle policies. The
dry run lists eight images from four registries - read from the chart, not a
list in the script. After the copy, `--check` ends `ok all 8 images are
mirrored`. Confirm each is a single-platform image, not a multi-platform index
missing its other platforms:

```bash
for r in grafana/grafana kube-state-metrics/kube-state-metrics prometheus/prometheus; do
  aws ecr describe-images --repository-name $PROJECT-mirror/$r --region $AWS_REGION \
    --query 'imageDetails[0].[imageTags[0],imageManifestMediaType]' --output text
done
```

Each is `...manifest.v2+json` or `...oci.image.manifest.v1+json`. `$r` is set by
the `for` line.

## 4. Container Insights works despite the hop limit

The node launch template stops pods reaching instance metadata. The agent needs
it - and runs on the host network, where the limit does not bite:

```bash
# variable form
kubectl --context $CLUSTER_NAME -n amazon-cloudwatch get daemonsets \
  -o jsonpath='{range .items[*]}{.metadata.name}{" hostNetwork="}{.spec.template.spec.hostNetwork}{" ready="}{.status.numberReady}{"\n"}{end}'
aws cloudwatch list-metrics --region $AWS_REGION --namespace ContainerInsights \
  --dimensions Name=ClusterName,Value=$CLUSTER_NAME --query 'length(Metrics)'
aws logs describe-log-groups --region $AWS_REGION --log-group-name-prefix /aws/containerinsights/$CLUSTER_NAME \
  --query 'logGroups[].logGroupName' --output text

# expanded
aws cloudwatch list-metrics --region us-east-1 --namespace ContainerInsights \
  --dimensions Name=ClusterName,Value=mongo-dcu-pipeline-qa --query 'length(Metrics)'
```

`cloudwatch-agent hostNetwork=true ready=2`; several hundred metrics (464 on the
live run) within minutes; and `/aws/containerinsights/mongo-dcu-pipeline-qa/performance`
- a log group Terraform did not create and will not destroy. `status.sh` lists
it now.

The add-on runs three pods and no more: `kubectl --context $CLUSTER_NAME -n
amazon-cloudwatch get pods` shows a controller and two agents - no Fluent Bit,
no second node-exporter.

## 6. Prometheus and Grafana

Prometheus, through the API server:

```bash
kubectl --context $CLUSTER_NAME get --raw "$PROM/api/v1/targets?state=active" \
  | jq -r '.data.activeTargets | group_by(.labels.job) | .[] | "\(.[0].labels.job): \(map(.health) | group_by(.) | map("\(.[0])=\(length)") | join(" "))"'
kubectl --context $CLUSTER_NAME get --raw "$PROM/api/v1/rules?type=alert" \
  | jq -r '.data.groups[] | select(.name=="mongo-dcu-pipeline") | .rules[] | "\(.name) \(.state)"'
```

Every job `up` - including `mongo-dcu-pipeline-app`, which can take a minute to
appear after the application installs - and nothing for etcd, the scheduler or
the controller manager. The application's three rules, `inactive`.

Grafana, through a port-forward, with the password in a file rather than on a
command line:

```bash
kubectl --context $CLUSTER_NAME -n monitoring port-forward svc/$RELEASE-grafana 3000:80 &
umask 077
kubectl --context $CLUSTER_NAME -n monitoring get secret $RELEASE-grafana -o jsonpath='{.data.admin-password}' \
  | base64 -d | xargs printf 'machine localhost login admin password %s\n' > $S/grafana.netrc
for ds in prometheus cloudwatch; do
  curl -s --netrc-file $S/grafana.netrc localhost:3000/api/datasources/uid/$ds/health | jq -c '{status,message}'
done
curl -s --netrc-file $S/grafana.netrc 'localhost:3000/api/search?type=dash-db&query=mongo' | jq -r '.[].title'
```

Both `"status":"OK"` - the CloudWatch one saying it queried both the metrics and
logs APIs, which proves Grafana's IRSA role and the `monitoring` endpoint
together. Two dashboards: `mongo-dcu-pipeline` and `mongo-dcu-pipeline - AWS
managed services`. Then a real CloudWatch query, as a panel would send it:

```bash
curl -s --netrc-file $S/grafana.netrc -H 'Content-Type: application/json' -X POST localhost:3000/api/ds/query -d '{
  "from":"now-1h","to":"now","queries":[{"refId":"A","datasource":{"type":"cloudwatch","uid":"cloudwatch"},
  "queryMode":"Metrics","region":"default","namespace":"AWS/DocDB","metricName":"CPUUtilization",
  "dimensions":{"DBInstanceIdentifier":"*"},"matchExact":false,"statistic":"Average","period":"300"}]}' \
  | jq -r '.results.A | "status=\(.status) series=\([.frames[]?.schema.name] | join(","))"'
```

`status=200 series=mongo-dcu-pipeline-docdb-qa-1`. Delete `$S/grafana.netrc`
when done.

## 7. The failure-rate alert

Files, not assumptions. Upload failures:

```bash
# variable form
for n in 1 2 3; do aws s3 cp samples/one-bad-line.txt s3://$PROJECT-$ENV-input-$ACCOUNT_ID/bad-$n.txt; done
# about a minute, then:
kubectl --context $CLUSTER_NAME get --raw "$PROM/api/v1/alerts" \
  | jq -r '.data.alerts[] | select(.labels.alertname|test("MongoDcu")) | "\(.labels.alertname) \(.state)"'
kubectl --context $CLUSTER_NAME get --raw "$AM/api/v2/alerts" \
  | jq -r '.[] | select(.labels.alertname|test("MongoDcu")) | "\(.labels.alertname) \(.status.state) receivers=\([.receivers[].name]|join(","))"'

# expanded
aws s3 cp samples/one-bad-line.txt s3://mongo-dcu-pipeline-qa-input-950639281723/bad-1.txt
```

`$n` is set by the `for` line. `MongoDcuRunFailureRateHigh firing`, and in
Alertmanager `active receivers=null` - it arrived and goes nowhere, by design.

**The live run needed more files than this, and that was a bug.** On the image
built before Phase 10's fix, the first failures after a pod started never
raised the alert: the `failed` series did not exist until they happened, and
`increase()` cannot see the event that creates a series (issue 25). With the
current image every series exists at zero, and the first failed files count.

## 8. The polling-stalled alert

A healthy pod that stops making progress is the failure this rule exists for.
The live run first tried a real one - removing `AWS_DEFAULT_REGION`, the issue 17
hang - and the pod polled normally: the EKS webhook now injects that variable
itself. So the stall is simulated with an hour-long poll interval, which gives
the rule exactly what it measures - a pod passing its probes with a counter that
has stopped:

```bash
# variable form
kubectl --context $CLUSTER_NAME -n $ENV patch configmap $PROJECT-app --type merge -p '{"data":{"POLL_INTERVAL_SECONDS":"3600"}}'
kubectl --context $CLUSTER_NAME -n $ENV rollout restart deploy/$PROJECT-app
# watch the state change - about 1 minute to pending, 5 more to firing:
kubectl --context $CLUSTER_NAME get --raw "$PROM/api/v1/alerts" \
  | jq -r '.data.alerts[] | select(.labels.alertname=="MongoDcuPollingStalled") | "\(.state) since \(.activeAt)"'

# expanded
kubectl --context mongo-dcu-pipeline-qa -n qa patch configmap mongo-dcu-pipeline-app --type merge -p '{"data":{"POLL_INTERVAL_SECONDS":"3600"}}'
kubectl --context mongo-dcu-pipeline-qa -n qa rollout restart deploy/mongo-dcu-pipeline-app
```

On the live run: restart at 19:17:48, `pending` at 19:19:08, `firing` at
19:24:03 - its five-minute `for`, to the poll - and `active` in Alertmanager
with no receiver. The pod was `ready=true restarts=0` throughout: nothing
crashed, which is the point. Put it back with the same `helm upgrade --install` as section 5,
then `kubectl rollout restart` - Helm does not restart a pod for a ConfigMap
someone else edited.

`78 to destroy`, then `22`. **The dry run is not empty** - it lists
`/aws/containerinsights/mongo-dcu-pipeline-qa/performance`, the log group the
agent created. Delete it with `nuke.sh --skip-dev`, or by hand:

```bash
aws logs delete-log-group --log-group-name /aws/containerinsights/$CLUSTER_NAME/performance --region $AWS_REGION
```

Then `./scripts/status.sh`: `billable resources running: 0`, and the log group
section `none`. The mirror stays - it is part of the permanent shared stack.

## What this phase does not prove

- **prod's monitoring.** The observability module is wired into prod and its
  plan validates; nothing was applied there.
- **The first-failure fix live.** Issue 25's fix is unit tested; the image that
  carries it was not rebuilt and deployed in this phase's session.
- **A real hang raising the stall alert.** The alert was proven with a
  simulated stall; the hang it was modelled on no longer reproduces on this
  platform.
- **Grafana dashboards by eye.** The data sources and queries were checked
  through the API. Opening the dashboards in a browser is the next step anyone
  reviewing this would take.
- **Splunk and Jenkins.** Phases 11 and 12.
